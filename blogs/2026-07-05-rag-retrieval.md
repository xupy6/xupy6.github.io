# RAG 的问题经常不在向量库

之前调 RAG 的时候，总会下意识怀疑 embedding 或向量库不够好。后来做多了才发现，大部分问题其实更早就埋下了。

最常见的是切分太随意。一段文档如果按固定长度切，很容易把定义、条件、结论拆开。模型检索到其中一半时，看起来像有依据，实际上上下文是断的。聊天记录这种数据更明显，一句话单独拿出来可能完全变味，必须带上前后几轮。

我现在更倾向于这样处理：

- 先按自然边界切，比如段落、对话轮次、章节。
- 每个 chunk 保留来源、时间、人物、主题这些 metadata。
- 初筛用向量召回，后面再做一次 rerank。
- 如果分数很低，宁愿让模型说“不确定”，不要硬编。

RAG 也会影响速度。默认全开检索会让对话变慢，尤其是用户只是随便问一句的时候。所以我更喜欢把 RAG 做成增强开关：普通聊天先走角色设定和短上下文，需要查细节时再检索。

这个取舍不酷，但比较像真实产品。用户不关心你后面跑了多少链路，用户只感觉“它回得慢不慢、像不像、有没有乱说”。
